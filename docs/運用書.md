# p-p-TechNews 運用書

更新日: 2026-10-11<br>
対象: `p-p-TechNews` リポジトリを引き継ぐ人・AIエージェント

## 1. このリポジトリの目的

週次の技術レーダーを作成・公開する。各週のHTML記事が人間向けの正本で、`build.mjs` が一覧やAI検索用の派生物を生成する。目的は、既存プロジェクトやLinear案件に関係する変化を見つけることと、AI自身の知識カットオフ後の変化を追うこと。

日常の構成・生成コマンドは [README.md](README.md) を参照する。この文書は、週次作業、公開の境界、クラウドPCへの引き継ぎに必要な運用をまとめる。

## 2. 週次号の流れ

号の日付は対象週の日曜日。対象期間は同じ週の月曜日から日曜日まで。

1. `sources.mjs` などで候補を集める。YouTubeは候補発見用で、採用事実は公式ドキュメント・公式ブログなどの一次情報で確認する。
2. 採用理由、対象期間内の公開日、一次情報URL、関連する実在のLinear案件（または直接該当なし）を記録する。
3. 採用記事を選び、必要な図解を記事単位で生成する。専用手順は `skills/diagramize/SKILL.md` と `diagram-jobs.mjs` を参照する。
4. `node build.mjs` で週次HTMLと一覧を生成し、必要な索引も更新する。
5. 図解ジョブの完了状態、HTMLへの埋め込み、候補取得の失敗、一次情報、受入テストを確認する。生成成功とHTML埋め込み成功は別々に確認する。
6. Git差分を確認し、意図した週次成果物だけをコミット対象にする。自動コミット・プッシュは行わない。

候補不足を埋めるために根拠の弱い記事を採用しない。少数号にする場合は、候補総数・一次情報確認数・不採用理由を号に残す。取得失敗や未完了図解を「情報なし」「完了」と丸めない。

## 3. 公開の手順と停止条件

公開スクリプトは `publish-technews.mjs`。公開先は `firebase-auth-poc/wrangler.toml` で指定する既存Worker `technews-private-auth-test`。Node.js 22以上と、lockfileどおりの `npm ci` が前提。Wranglerは固定devDependency `4.134.0` を使う。

対象号の日曜日を `YYYY-MM-DD` で指定する。

```bash
node publish-technews.mjs --preflight YYYY-MM-DD
node publish-technews.mjs YYYY-MM-DD
```

`--preflight` はローカル検査であり、デプロイしない。通常公開コマンドは検査を再実行し、ゲートを通った場合だけデプロイと公開後スモーク確認へ進む。確認済みの初回公開状態がない環境では通常公開は停止する。初回登録モード `--first-deploy` は自動化から実行せず、対象・差分・Worker・コマンド・復旧手順を提示して、実行直前のユーザー明示確認を得た場合だけ使う。

次の場合は公開しない。

- 対象日や生成済みHTML・一覧に不整合がある。
- 必須の受入テストや成果物検査が失敗した。
- 採用記事に図解未完了・未埋め込みが残る（許可されたアクセシブルなSVGフォールバックは例外）。
- Worker名、公開対象の除外設定、または認証状態が想定と異なる。
- preflight、デプロイ、公開後スモークのいずれかが失敗した。

認証方式、許可UID、Cookie、ログイン経路、公開先Workerを勝手に変更しない。公開書込APIやデータベースを追加しない。自動ロールバック、Git commit、pushもしない。スモーク失敗は公開成功として報告せず、結果と対象号を記録して人へ知らせる。

## 5. クラウドPCへ移すとき

### リポジトリのコピーだけで移るもの

ソース、週次HTML、テスト、リポ内スキル、README、設計資料など、Gitで管理しているファイル。分割ZIPを使う場合は全パートを同じフォルダへ展開する。`.technews-release-state.json` はGitと静的配信から除外するローカル状態であり、今回のZIPにも含まれていない。

### 別途設定・確認が必要なもの

- Node.js 22以上と `npm ci`。
- Codex Desktopのプロジェクト登録、および必要ならローカル自動化の再作成・設定読み戻し。GitHubへのソース移行だけでは実設定は移らない。クラウドPCでは実行環境、対象プロジェクト、日曜21:00 JST、実行プロンプトを確認してから再作成する。
- 現在の自動化は元PCのローカル実行である。クラウドPCでは実設定が移行していない前提で、実行環境、対象プロジェクト、日曜21:00 JST、実行プロンプトを確認してから再作成する。
- NotebookLMなど外部サービスを使う工程の、そのPC上での利用可否と認証。
- Cloudflare/Wranglerの認証。秘密値や認証ファイルをZIP・Git・公開アセットへ入れない。
- 新しいPCでの対象Worker、認証境界、除外設定の読み取り確認。ローカルのrelease stateファイルがコピーされていても、そのPCでの認証や最新の公開状態を証明しない。

自動化の実設定・実行履歴はユーザーPC側にあり、リポジトリだけでは引き継がれない。ZIP内の本書・README・設計資料を読み、次にCodexの自動化設定と必要な認証を移行先で個別に確認する。
